# C0 — W1 team conventions: паралелізм і ролі

Статус: **виконано** (документаційна задача, без коду) · Власник: implementer ·
2026-11-25 · Джерело: `docs/decisions.md` §2a.

## Навіщо

У W1 команда помилково розмножила ролі замість того, щоб запускати незалежні
задачі паралельно в сесіях одного учасника. Ця нотатка фіксує конвенцію
(дубльована в `docs/decisions.md` §2a) і практичний чекліст, щоб наступні хвилі
не повторювали помилку.

## Конвенція

1. **ROLES.** Лише 8 вбудованих ролей профілю: scout, investigator, expert,
   implementer, test_writer, browser_tester, reviewer, final-reviewer.
   Роль `implementer` рівно одна. Варіанти ролей (backend/security/frontend-
   implementer) не створюються: обсяг роботи описується в задачі, а не в новій
   ролі чи імені учасника.
2. **PARALLELISM.** Один учасник може виконувати кілька незалежних готових задач
   паралельно в окремих сесіях. Дублікати учасників для паралелізму не
   створюються — незалежні задачі призначаються тому самому учаснику. Другий
   `implementer` — лише після виміряного ліміту провайдера/конкурентності, з
   зафіксованим evidence в `docs/decisions.md`.
3. **CONFLICT CONTROL.** Безпека паралелізму = неперетинні write-scope + єдиний
   власник на спільний файл:
   - `Cargo.toml`/`Cargo.lock` — один власник (T15);
   - `http/mod.rs` + `api/mod.rs` — scaffolding (I0), після нього read-only;
   - роутери монтуються один раз;
   - API-задачі пишуть у власні файли.
4. **EVIDENCE.** W0: T04 + T05 на одному implementer; W1: T10 і T11 паралельно,
   далі T07/T08/T09/T12 паралельно — усі на тому самому implementer.

## Практичний чекліст

- [ ] Незалежні готові задачі призначати **одному** учаснику (окремі сесії), а не
      створювати дублікатів членів команди.
- [ ] Не вигадувати ролі: тільки 8 вбудованих; `implementer` — одна роль,
      специфіка пакета — в описі задачі.
- [ ] Конфлікти описувати через `inScope` + `deps`, а не через нові ролі чи
      учасників; спільний файл має рівно одного власника.
- [ ] `Cargo.toml`/`Cargo.lock` — тільки T15; `http/mod.rs` + `api/mod.rs` — I0,
      далі read-only; роутери — один раз у scaffolding.
- [ ] Другого `implementer` створювати лише за наявності виміряного
      provider/concurrency-обмеження; доказ внести в `docs/decisions.md`.
- [ ] У звіті — точні змінені шляхи та виконані evidence-команди.
