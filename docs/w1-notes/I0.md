## 3. Auth guard — фінальна сигнатура, placeholder-тіло

`http/middleware/mod.rs`:

```rust
pub async fn auth_guard(State<AppState>, Request, Next) -> Response
```

* **public**: `POST /api/pin/verify`, `GET /api/auth/session`, `POST
  /admin/login`, `POST /admin/logout` → запит іде далі без cookie;
* **admin**: `/api/settings*`, `/api/admin/*` (включно з maintenance backup) →
  непорожній cookie `auth_token`;
* **device**: решта змонтованих `/api/*` → непорожній cookie `device_token`;
* немає credential → `401 {"error":"token_required"}`; порожній credential →
  `401 {"error":"invalid_token"}`.

**PLACEHOLDER:** тіло перевіряє лише наявність/непорожнечу cookie; воно не
хешує і не читає `device_access`/`settings` (це поза inScope I0). Тому
«будь-який непорожній токен проходить» — це ТИМЧАСОВО і **мусить бути
замінене T10 до інтеграції/деплою**. Контракт заміни: T10 редагує лише тіло
`auth_guard`/приватних хелперів у `middleware/mod.rs`, зберігає сигнатуру,
константи `DEVICE_TOKEN_COOKIE`/`ADMIN_TOKEN_COOKIE`, коди 401 і назву
`middleware::auth_guard`; `http/mod.rs` при цьому не чіпається. Доступ до БД —
через `State<AppState>::db()` (додаткові поля стану — теж зона T10).

* `server/src/http/mod.rs`, `api/mod.rs`, `middleware/mod.rs` — read-only для
  T07–T11 (middleware — власність T10).

## 6. Відкриті ризики / передача далі

* Placeholder-guard **не є авторизацією**: T10 зобов'язаний замінити його тіло
  (SHA-256 `device_token` → `device_access.token_hash`, перевірка
  `status='allowed'`, `auth_token` → `settings.admin_token`) до будь-якого
  деплою. W1-код не пушиться/не деплоїться, прод недоторканий.
* `POST /api/bookmarks/dump`-стиль method mismatch: guard стоїть на matched
  route, тому неправильний метод на відомому шляху теж спершу отримає 401 —
  фінальну поведінку 405/401 для таких кейсів фіксує T10/E2E.
* 501-формат (`{"error":"not_implemented"}`) — тимчасовий; кожна група
  замінює свої відповіді на legacy-контракт із T03-фікстур.
