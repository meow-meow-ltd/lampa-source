## 2. Дизайн / чому саме так

1. **Два режими.** За замовчуванням — *spawn*: бінарник + свіжа синтетична БД +
   випадковий порт. `BASE_URL=…` (з `E2E_ADMIN_PASSWORD`, `E2E_TOTP_SECRET`) —
   матриця проти вже запущеного сервера: збірка/БД/спавн/логи пропускаються і це
   явно пише у виводі. Обидва режими перевірені (§5).
2. **Синтетична v7-БД** — `deploy/scripts/make_synthetic_db.py --out <tmp>`;
   після побудови читаються лише факти (`journal_mode=delete`,
   `schema_version=7`, лічильники рядків). Ні DDL, ні WAL, ні `_sqlx_migrations`,
   ні один запис у `/opt/lampa/data` чи `/opt/lampa/staging-data` (порти 9119 не
   торкаються взагалі). Адмін-облікові дані — канонічні константи
   `ADMIN_PASSWORD`/`ADMIN_TOKEN` із самого білдера (одне джерело правди,
   реєструються як секрети).
3. **Бінарник.** Кандидати: `LAMPA_SERVER_BIN`, `../.cargo-target/{release,debug}`,
   `server/target`, `target`; серед свіжіших (новіших за найновіший
   `server/**.rs`/`Cargo.*`) надається перевага `release`. Якщо бінарник
   застарілий — офлайн-збірка у закріпленому образі:
   `cargo build --release --locked --offline` у `lampa-rust-builder:1.100.0`
   (без жодного мережевого доступу; `Cargo.lock` не змінюється). Якщо **спільне
   дерево не компілюється** (інший редактор посеред змін) — ранер не падає
   мовчки: він друкує `WARN: offline build failed …` з хвостом помилок cargo і
   явно тестує попередній бінарник; якщо бінарника немає взагалі — `FATAL` і
   ненульовий код. Такий фолбек у цьому виконанні спрацював один раз
   (бінарник 23:58, у дереві були незавершені `server/src/bookmarks/*`), після
   фіксу сусіда збірка проходить знову.
4. **Cookie-jar як модель браузера.** Кожен `Set-Cookie` застосовується до
   jar (`Max-Age=0`/минулий `Expires` → видалення), тож «наступний запит після
   revoke» — це саме те, що побачить браузер: перший запит → `401 invalid_token`
   + очищення cookie, далі jar порожній → `401 token_required`. Окремо той самий
   (відкликаний) токен пред'являється напряму в заголовку — щоб довести, що
   відкликаний токен відхиляється і на захищеному маршруті, і на
   `/api/auth/session`.
5. **TOTP без залежностей** — HMAC-SHA1/6/30 на `node:crypto`, base32-декодер
   вручну; «хибний» код — перший із 6 цифр, що не збігається з жодним із
   трьох прийнятих кроків (±30 с), як у `server/tests/auth/support.rs`.
6. **Rate limits** ключуються по IP: `cf-connecting-ip` приймається лише від
   loopback-пера (T10), тож запити з `203.0.113.44` (TEST-NET-3) і
   `198.51.100.7` (TEST-NET-2) — окремі ключі й не псують основний потік;
   10 невдач → `429` **до** TOTP; 5 невдач на одному пристрої → `blocked`, жодного
   `403`.
7. **Re-pair = 0** визначається явно: `кількість успішних POST /api/pin/verify − 1`,
   плюс первинний токен має лишитися валідним (без ротації) після двох
   «reload»-запитів.
8. **Гігієна секретів.** Усі секрети (TOTP, видані токени, адмін-пароль/токен,
   хибні PIN) реєструються; **кожен** рядок виводу проходить `redact()`
   (плюс blanket-маски `64-hex` і `device_token=/lampa_session=/auth_token=`),
   а в кінці вивід сканується ще раз — `leak check: 0 of 5`. Окремий рядок
   матриці сканує **лог сервера** (`RUST_LOG=debug`, тобто найголосніший рівень,
   де живуть rejection-логи guard-а) після його зупинки: `156 log lines,
   0 of 5 secrets, 0 cookie pairs`.
9. **Cleanup у `finally`** — `SIGTERM` → `SIGKILL`, `rm -rf` тимчасового
   каталогу; жодного процесу/файлу не лишається (перевірено `pgrep` + відсутність
   `/tmp/lampa-t14-*`).
10. **Браузерний чек** (`browser_reload.mjs`) — офлайн і без установок:
    статичний рут `build/web` + проксі `/api/*` і `/admin/*` на той самий origin
    (справжні cookie), усі не-local ресурси `abort` (мережі немає), Playwright
    береться з локального кешу (`~/.npm/_npx/*/node_modules/playwright`, Chromium
    ревізія 1255 у `~/.cache/ms-playwright` — збігається). Лічиться саме
    **document load** (SPA-router pushes `/?title=…` рахуються окремо і в критерій
    не входять); поріг — 5 навігацій / 5 с (S8 §7.7). Якщо Playwright/Chromium
    недоступні — результат `{"status":"skip"}` → **O4**, HTTP-матриця лишається
    авторитетною. Додано seed `localStorage.language`, бо інакше свіжий профіль
    зупиняється на виборі мови (`loadApp()` → `LangChoice.open`) і
    `checkDevice()` не викликається — reload-loop питання стосується вже
    налаштованого пристрою.

## 4. Реальний браузер (reload-loop) — виконано, O4 не знадобився

Чек виконався офлайн на вже встановленому Playwright 1.65.1 + Chromium 1255
(нічого не встановлювалося), тому **O4 як «недоступний інструмент» не
застосовується**; шлях `skip → O4` у коді лишається на випадок середовища без
браузера. Результат:

```text
PASS browser_reload_loop_check — unpaired: gate visible, 1 document load(s) + 0 router push(es) in 5s;
PIN verify answered 200; PIN paired: gate hidden, 1 PIN verify request;
cookies: lampa_session HttpOnly + readable device_token (same value);
reload: 1 document load(s) + 2 router push(es) in 5s; reload: still paired, 0 re-pair;
revoke: admin action revoked the paired device row id=16; revoke: gate returned, 1 document load(s) + 0 router push(es) in 5s
```

Що це доводить (S8 §6/§7.7, T12 §3/§6):

| Сценарій | Очікування | Факт |
|---|---|---|
| непарний завантаження | гейт видимий, **0 reload-loop** (<5 document load / 5 с) | 1 document load, 0 router push |
| після PIN | гейт схований, рівно **1** `/api/pin/verify` | 1 запит, `200` |
| cookies у C | `lampa_session` HttpOnly + читабельний `device_token`, однакове значення | PASS |
| reload (еквівалент `checkDevice()`) | гейт не з'являється, **0 re-pair**, `<5` load/5 с | 1 document load (+2 SPA-router pushes), гейт ні, 1 PIN-запит усього |
| admin revoke → reload | гейт повертається (revocation gate), без циклу | row id=16 відкликано, гейт повернувся, 1 document load |

Обмеження: це **headless Chromium** на цьому хості. Реальні Safari/TV-пристрої
(S8 §11) офлайн недоступні — якщо команда захоче такий прогін, це окремий
відкритий пункт для хвилі з реальним пристроєм; він **не входить** у
acceptance T14 (де O4 стосується саме недоступності інструмента).

## 6. Спостереження (не блокують, межу T14 не порушують)

1. **`GET /api/auth/session` → 401 без `Cache-Control: no-store`.** T10 §2.4
   згадує `no-store`, але в `server/src/http/api/auth_session.rs` цей заголовок
   ставиться лише на гілці `200` (`no_store()`), тоді як `unauthorized()` його не
   додає. Рядок матриці це **фіксує як спостереження**
   (`note session 401 Cache-Control: null`), а не як FAIL: acceptance T14
   вимагає саме коди `token_required`/`invalid_token`. Рішення — за власником
   T10 (додати `no_store()` до `unauthorized()` або прибрати з формулювання).
2. **`POST /api/values` → `400 {"error":"Missing or invalid keys parameter"}`**
   під час завантаження застосунку (не-auth маршрут, власник T07). На reload-loop
   не впливає (401 немає), зафіксовано лише для власника маршруту.
3. **Мова в `localStorage`** обов'язкова для входу в `checkDevice()`; без неї
   застосунок чекає на вибір мови. Браузерний чек сіє `language=en` (див. §2.10).
