Точний dispatch (початок `async fn main`, **до** `Config::from_env()`):

```rust
// Maintenance CLI dispatch (W1/T11): `backup`/`restore`/`check` run before
// any server configuration, so the operational commands never touch the
// HTTP stack. `run_cli` initialises its own tracing and returns the exit
// code (0 success, 1 failure, 2 usage).
let args: Vec<String> = std::env::args().skip(1).collect();
if db::backup::is_cli_invocation(&args) {
    std::process::exit(db::backup::run_cli(&args));
}
```

Чому `run_cli`, а не `cli`: формулювання задачі згадує `cli(&args)`, але
acceptance-критерій вимагає сніпет із T11 §7, який викликає
`is_cli_invocation` + `run_cli`; `run_cli` — це тонка обгортка над `cli`, що
додає tracing (stderr, `RUST_LOG`, fallback `info`), stdout-JSON та exit code
`0/1/2`. Використано §7 дослівно. Серверний шлях (без підкоманди) не
змінений: `args` лише читаються, `Config::from_env()` і все подальше
виконується як раніше.

## 2. Зняття `dead_code`

`db/backup.rs` більше не містить жодного `allow(dead_code)` (ні module-level,
ні field-level) — evidence §4, рядок 2.

Після видалення `#![allow(dead_code)]` `cargo clippy --all-targets -- -D
warnings` виявив **одну** справжню dead-code помилку в production-таргеті:
`CliReport.command` читався лише unit-тестом (`assert_eq!(…command, "backup")`,
`cfg(test)`), тому non-test бінарник вважав поле мертвим:

```
error: field `command` is never read
   --> src/db/backup.rs:1034:9
```

Вирішено без придушення лінта: success-path `run_cli` тепер логує підкоманду
(`info!(command = report.command, "maintenance CLI succeeded")`). Це єдине
використання поля в production-коді; stdout-JSON, exit codes і файлові
операції не змінені (додається один INFO-рядок у stderr, як і решта
tracing-логу CLI). Field-level `#[allow(dead_code)]` відкинуто — він зберіг би
придушення. Жодна backup/restore/verify-функція, флаг або формат відповіді не
змінені.
