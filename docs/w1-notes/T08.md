## Legacy-семантика (збережена)

| Маршрут | Поведінка |
|---|---|
| `GET /api/bookmarks/dump` | `Content-Type: text/plain; charset=utf-8`, тіло — JSON; `version = MAX(bookmark_events.id)` для профілю (0 якщо подій немає); рядки `ORDER BY updated_at ASC, id ASC`; `data` — JSON-текст **як є** |
| `GET /api/bookmarks/changelog?since=` | JSON; `version = MAX(id)`; події `id > since ORDER BY id ASC`; `add` → `{action,id,type,card_id,data,updated_at}` (`entity_id` перейменовано в `id`), `update` → `{action,entity_id,updated_at}`, `clear`/`remove` → `{action,entity_id}`; невідома дія деградує до `remove` (як у Node) |
| `POST add` | `type` trim + `parseInt(card_id)` обов'язкові (`400 Invalid payload`); `data` — непорожній рядок (`400 Missing data`); новий рядок → подія `add` з `entity_id = bookmarks.id`, існуючий → UPDATE + подія `update` |
| `POST remove` | з `id != 0` — DELETE за id + подія `remove` **завжди** (навіть якщо рядок не знайдено); без `id` — пошук `(profile,type,card_id)`, невідомий → `200 {secuses:true}` без події |
| `POST clear` | вимагає `type == "group"` і непорожній `group` (інакше `400 Invalid payload`); видаляє один тип; подія `clear` з `entity_id = group` (TEXT у typeless-колонці) |
| `POST sync` | `data` — рядок JSON (`raw ? JSON.parse(raw) : {}`); невалідний → `400 Invalid JSON`; **одна транзакція**: DELETE всіх bookmarks профілю → upsert кожного прийнятного card (`parseInt(card.id)`) → подія `add` на кожен; будь-яка помилка → ROLLBACK (без часткових bookmarks/events) |
| `GET /api/timeline/dump` | `Content-Type: text/plain; charset=utf-8`; `{version, timelines}`; `version = MAX(timeline_events.id)`; рядки `ORDER BY updated_at ASC`; кожен `data` парситься і `hash` примусово встановлюється (невалідний JSON → `{hash}`) |
| `GET /api/timeline/changelog?since=` | JSON; `{version, timelines}`; події `id > since ORDER BY id ASC`; **без LIMIT** (250/250 перевірено) |
| `POST /api/timeline/update` | `payload = body.params || body`; `hash` — непорожній рядок (`400 Missing hash`); `percent/time/duration = value || 0`; `data = {hash,percent,time,duration,profile}`, де `profile = payload.profile || profileId`; upsert `(profile_id, hash)` + окремий `timeline_events`; `hash` — TEXT, без обрізання (16-символьний fixture-hash збережено) |

Спільне: профіль з `profile`/`x-profile` заголовка, далі `body.profile` (timeline —
ще `body.params.profile`); `1`-в-1 legacy `parseInt` (префіксні цифри, NaN → 0);
`Content-Type` запиту не має значення — приймаються JSON і плоскі
`application/x-www-form-urlencoded` поля (реальний jQuery-клієнт Lampa шле форму).

## Свідомі відхилення (plan §3.6 п.6)

1. **Сирі SQL-помилки не віддаються**: legacy `500 {secuses:false,error:err.message}`
   → `500 {"secuses":false,"error":"internal_error"}`, деталі лише в серверний лог;
   `503 {"secuses":false,"error":"database_unavailable"}` для fail-closed стану.
2. `Content-Type` запиту ігнорується (як у T10 PIN): legacy body-parser парсив лише
   за заголовком; це client-friendly розширення, форма/JSON розпізнаються за тілом.
3. `sync`: `entity_id` події = фактичний `bookmarks.id` після upsert; Node брав
   `this.lastID || null`, що на конфліктному UPDATE дає застарілий/NULL id. Фікстури
   15–23 цього не пінять (sync-відповідь лише `{secuses:true}`), а фактичний id —
   послідовна семантика «add event вказує на рядок».
4. Вкладені `urlencoded` ключі (`params[hash]=…`, `data[type][0][id]=…` з qs
   `extended=true`) не розгортаються; реальний Lampa-клієнт шле плоскі поля.
5. Додано `Cache-Control: no-store` на всі відповіді (plan §3.6 п.8; у T03-фікстурах
   цього заголовка немає, бо Node-референс його не ставив; Content-Type/статус/тіло
   збігаються з фікстурами).
