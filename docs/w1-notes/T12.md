## 2. Чому саме так

1. **Джерело правди — сервер.** T10 віддає `lampa_session` (HttpOnly) + у C
   читабельний `device_token` тим самим значенням. Клієнт більше не вирішує
   «пускати/не пускати» за `document.cookie`, тому HttpOnly-модель B працює, а
   Safari ITP-ліміт 7 днів зникає (S8 §1, §6B).
2. **`fetch` обрано навмисно:** він не проходить через 401-обробник
   `src/utils/reguest.js`, тому навіть при старому сервері без
   `/api/auth/session` (misdeploy «клієнт-першим») буде гейт, а не нескінченний
   reload-loop (S8 §6B, §7.7; у лабі без винятку — 5 навігацій/5 с).
3. **401 ≠ помилка для bootstrap.** T10 повертає **401 `token_required`**
   (не `200 {paired:false}`) для неспареного пристрою (`docs/w1-notes/T10.md`
   §5.1). `fetch` резолвиться, `response.json()` дає `{error:"token_required"}`,
   `res.paired` відсутній → `PINGate.show()`; жодного `location.reload` у
   `checkDevice` немає. **T14 має кодувати саме це очікування:** unpaired → 401 →
   гейт без навігаційного циклу; paired → 200 → застосунок.
4. **Старі клієнти (C).** Старий бандл у HEAD не змінювався: `checkDevice`
   читає `device_token`, `pin_gate` пише його, 401-обробник чистить. T10 у C
   (типово `DEVICE_LEGACY_COOKIE=1`) видає обидва cookie на PIN і приймає legacy
   `device_token` у guard; `/api/auth/session` приймає legacy та перевидає
   `lampa_session` тим самим токеном без ротації та без re-pair (T10 E2E).
   Тому вже виданий токен не вимагає повторного PIN ні старим, ні патченим
   клієнтом.
5. **B-strict — не першим.** При `DEVICE_LEGACY_COOKIE=0` старий клієнт без
   readable-cookie отримає 401 → PIN (UX re-pair, не адмін-перепарування). Це
   відомий ризик порядку викатки S8 §7.8/§9.1; W1 лишається в C, cleanup — після
   ≥7 днів і підтвердження нового бандла (D6).
