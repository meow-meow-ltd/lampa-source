## 2. Backup core (`create_backup`)

* **SQLite backup API only**: `rusqlite::backup::Backup::new` + `step(-1)`.
  Жодного `cp`/`rsync`/`std::fs::copy` (evidence grep = 0), жодного читання
  файлу «сирими» байтами для створення артефакту.
* **Окреме read-only з'єднання**: `Connection::open_with_flags(db,
  SQLITE_OPEN_READ_ONLY | SQLITE_OPEN_NO_MUTEX)`, `busy_timeout=5 s`.
  Пул single-writer (SQLX) не позичається взагалі — сервер пише далі.
* **Чому один shot (`step(-1)`), а не `run_to_completion`**: SQLite рестартує
  покроковий backup з першої сторінки після кожного запису в source. При
  безперервному навантаженні single-writer-пулу це могло голодувати backup
  (виміряно: >460 s у debug-тесті). Один shot тримає SHARED-лок на час копії
  8 MiB (десятки мс), письменник чекає ці мс як на довгій читацькій транзакції;
  сервіс не зупиняється. `SQLITE_BUSY`/`LOCKED` ретраяться кожні 2 мс до 5 с.
* **Файл**: `/data/backups/database-YYYYMMDDTHHMMSSZ.sqlite` (UTC; лексикографічний
  порядок = хронологічний). Каталог створюється/ставить `0700`, файл
  пре-створюється `0600` (`OpenOptions::mode`) до запису SQLite, публікується
  атомарним `rename` (без вікна з umask-правами). Колізія в ту саму секунду
  (паралельні API-виклики) зсуває timestamp на +1 с, форма імені не змінюється.
* **Retention 14**: після публікації видаляються найстаріші артефакти понад 14;
  враховуються лише файли з точним шаблоном імені, сторонні файли в каталозі
  не чіпаються. Видалені файли логуються.
* **Перевірка**: на артефакті виконуються `PRAGMA integrity_check` (**мусить
  бути `ok`**), `PRAGMA quick_check` та SHA-256 (стрімінгово, 64 KiB буфер).
  `integrity_check`, `quick_check`, `journal_mode`, `sha256`, `bytes`, `ms`
  пишуться в лог (лише hash, без секретів); `journal_mode` нового артефакту —
  `delete` (SQLite default, WAL ніколи не вмикається).
* **Durability**: destination-з'єднання SQLite має default `synchronous=FULL`,
  тому `sqlite3_backup_finish` сам флашить артефакт; додатковий fsync не
  робиться (він додавав 40–100 мс варіативності й ламав бюджет ≤200 мс).
* Жодного DDL/VACUUM/ANALYZE; `journal_mode` не виставляється — лише
  читається/перевіряється.

## 3. Offline restore (`restore_database` / CLI)

Порядок fail-closed (жодного онлайн-restore, HTTP-роута немає):

1. `--offline` обов'язковий (інакше usage error; без нього restore не стартує).
2. Guard: `/opt/lampa/data` і `/opt/lampa/staging-data` (лексично + через
   `canonicalize`, щоб symlink не обійшов) відхиляються, поки не передано
   `--allow-prod-data`. Перевірка йде **до** будь-якого доступу до target.
3. Артефакт верифікується: `integrity_check=ok`, `quick_check=ok`,
   `schema_version=7`, `journal_mode=delete`; digest обчислюється.
4. Target offline-перевірка: жодних `-journal`/`-wal`/`-shm`; `BEGIN EXCLUSIVE`
   з `busy_timeout=0` доводить, що ніхто не тримає write-lock (інакше
   `database_in_use`, target не змінюється).
5. Байтова копія через `std::io` у temp-файл **у тому ж каталозі**, `0600`,
   fsync, атомарний `rename` поверх target (offline swap), fsync каталогу.
6. Post-check: `integrity_check`, `quick_check`, `journal_mode=delete`,
   `schema_version=7`, SHA-256 відновленого файлу == SHA-256 артефакту.
   Розбіжність → `restore_failed`.

`journal_mode` після restore — `delete` (header артефакту зберігається,
перевіряється явно). Target отримує `0600`.

CLI-контракт (`cli`/`run_cli`, exit codes 0/1/2):

```
lampa-server backup [--database PATH] [--backups-dir PATH]
lampa-server check --backup PATH
lampa-server restore --offline --backup PATH --database PATH [--allow-prod-data]
```

* `backup`: default database — `DATABASE_URL` (якщо валідний абсолютний
  `sqlite:`-URL), інакше `/data/database.sqlite`; default backups-dir —
  `<db parent>/backups`.
* `check`: `integrity_check` + `quick_check` + SHA-256 (друкований JSON).
* stdout — один JSON-об'єкт; stderr — tracing-логи (integrity/sha) та
  `{"ok":false,"error":"<code>"}` при помилці. Usage-помилки → exit 2.
* Restore **не** робить `docker stop/start` (це deploy-зона): оператор зупиняє
  сервіс, виконує `restore --offline`, стартує сервіс (plan §4.4).

## 4. Maintenance API

`POST /api/admin/maintenance/backup` (admin-клас, `auth_token`; guard T10
виконується **до** хендлера):

* успіх: `200 {"ok":true,"file":"/data/backups/database-…Z.sqlite","bytes":N,
  "sha256":"…","ms":N}`;
* fail-closed startup (guard БД не пройшов): `503 {"ok":false,"error":"db_unavailable"}`;
* мапінг безпечних кодів: `database_in_use` → 409; `missing_database` → 503;
  `invalid_path`/`unsafe_target`/`offline_required` → 400; решта
  (`integrity_check_failed`, `schema_mismatch`, `io_error`, `backup_failed`, …)
  → 500. Сирі SQL/драйверні тексти не серіалізуються (лише `code`, detail — у лог).
* Хендлер не приймає від клієнта жодного шляху/імені файлу → path traversal
  неможливий. Робота виконується в `spawn_blocking` (rusqlite синхронний),
  backups-dir = сусідній `backups` каталог БД (`/data/backups` у проді).

Важливо (G2-02): важкі 8 MiB тести позначені `#[ignore]`, тому звичайний
`cargo test` їх **не** виконує — інакше release-тайминг змагався з паралельними
тестовими бінарниками і давав хибні >200 мс (G2 виміряв 4/4 провали
336/949/239/348 мс при default-parallel запуску попри те, що serially ті самі
тести вкладаються у бюджет). Окремий крок `backup-timing` у
`scripts/ci/run.sh` запускає лише ignored-тести, у release, з
`--test-threads=1`:

```
cargo test --release --bins -- --ignored --test-threads=1 --nocapture
```

(`--bins`, а не `--lib`: `lampa-server` — binary-only пакет, library target
немає; `cargo test --release --lib ...` завершується помилкою «no library
targets found».) `--nocapture` потрібен, щоб `eprintln!`-рядки з мс потрапили
у вивід кроку (PASS/FAIL-рядок друкує виміряні значення).

Крок додатково дає контейнеру **приватний tmpfs `/tmp`**
(`docker run --tmpfs /tmp:rw,size=256m`), бо цей хост ділить диск з іншими
контейнерами/агентами: навіть після серіалізації overlay-writeback додавав
першому 8 MiB-семплу 171–227 мс (один прогін — 935 мс) і робив гейт
flaky. З tmpfs виміри стабільні: **backup 66–73 мс, restore 95–96 мс** у
5/5 повторів. Ізоляція змінює лише середовище вимірювання: тест так само
створює реальну 8 MiB v7 БД, виконує SQLite backup API, перевіряє
0600/0700, retention 14, `integrity_check`+`quick_check`+SHA-256 і ті самі
бюджети 200/300 мс. `HEAVY_TEST_LOCK` (`tokio::sync::Mutex`) залишено
другим запобіжником: ручний `--ignored`-прогін із паралельним harness-ом
усе одно не міряє бюджет під конкурентним SHA-256. Логіка backup/restore
і пороги 200/300 мс **не** змінені.

## 7. Wiring для інтеграції (T10 завершує `main.rs`)

```rust
let args: Vec<String> = std::env::args().skip(1).collect();
```
