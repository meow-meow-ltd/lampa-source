## Навіщо локальний скрипт

У W0 push/PR заборонений, тому «CI зелений» = `scripts/ci/run.sh` з exit 0
(W0-5). GitHub Actions workflow доданий, але в W0 **не запускається** (W0-5, О11):
remote-run потребує окремого дозволу власника. Повний шестикроковий `--strict`
прогін — це G1; T05 сам по собі перевіряється без Rust-кроків, щоб не
серіалізуватися на крейті, який одночасно пише T04.

## Кроки та флаги

| # | Крок | Команда | Пропуск |
|---|---|---|---|
| 1 | fmt | `cargo fmt --check` у `lampa-rust-builder:1.100.0` | `--skip-rust` |
| 2 | clippy | `cargo clippy --all-targets -- -D warnings` (той самий контейнер) | `--skip-rust` |
| 3 | test | `cargo test` (той самий контейнер) | `--skip-rust` |
| 4 | contract | `python3 deploy/scripts/capture_api_golden.py --check` (T03) | `--skip-contract`; авто-SKIP, якщо артефакту T03 немає |
| 5 | frontend | `npm run build` (gulp; exit 0) | `--skip-frontend` |
| 6 | vitest | `npx vitest run` → guard проти baseline | `--skip-frontend` (обидва JS-кроки) |

Флаги: `--skip-rust`, `--skip-frontend`, `--skip-contract`, `--strict`, `--list`,
`--baseline-self-test`, `-h/--help`. `--strict` робить **відсутність** T03-артефакту
FAIL (команда G1); без нього contract авто-визначає наявність. `--list` друкує 6
кроків і виходить 0; `--baseline-self-test` перевіряє сам guard і не запускає vitest.
Кожен крок друкує рівно один `PASS`/`FAIL`/`SKIP`-рядок, у кінці — `ci summary`.

## Rust-кроки: тільки builder-контейнер

На хості немає Rust, тому кроки 1–3 виконуються рівно за рецептом `server/README.md`
(нічого не встановлюється на хост):

```bash
docker run --rm --user "$(id -u):$(id -g)" \
  -v /opt/lampa/source:/work \
  -v /opt/lampa/poc/cargo-cache:/cargo \
  -v /opt/lampa/.cargo-target:/target \
  -e CARGO_HOME=/cargo -e CARGO_TARGET_DIR=/target \
  -w /work/server lampa-rust-builder:1.100.0 \
  bash -c '<cargo fmt --check | cargo clippy ... | cargo test>'
```

Версії в образі: `cargo 1.100.0 (3acc79c0c 2026-11-05)`, `rustc 1.100.0
(0ef1bc386 2026-11-09)`, `rustfmt 1.11.0-stable`, `clippy 0.1.100`. Каталоги можна
перевизначити через `LAMPA_CARGO_CACHE` / `LAMPA_CARGO_TARGET` /
`LAMPA_RUST_BUILDER_IMAGE`. Якщо docker або образ відсутні — крок FAIL з підказкою
(скрипт не будує образ і не тягне мережу).

## Vitest baseline (W0-4)

Зафіксовано 2026-11-25, Node `v22.23.2`, vitest `0.32.4`:

```text
$ cd /opt/lampa/source && npx vitest run
 Test Files  4 failed | 11 passed (15)
      Tests  3 failed | 171 passed (174)
exit code 1
```

Failed files (саме вони, не більше): `spec/account_timeline.spec.js`,
`spec/account_backup.spec.js`, `spec/episode_menu.spec.js`, `spec/media_loading.spec.js`.
Guard (`vitest_baseline_guard.py`) падає **лише** на нових падіннях:

- будь-який failing file поза списком 4 → FAIL;
- `failed tests > 3` → FAIL;
- `passed tests < 171` → FAIL;
- рівно baseline або краще (відомий файл почав проходити) → PASS.

`account_timeline.spec.js` падає на рівні suite (`document is not defined`,
`status: "passed"` з непорожнім `message`), тому guard вважає файл failing також
за наявності `message`, а не лише за `status == "failed"`. Лікування upstream-тестів —
не P0 (W0-4), тому baseline не «зелений з нуля».

`--baseline-self-test` синтезує 5 звітів і перевіряє поведінку guard: baseline-equal →
accept, injected new failing file → reject, extra failed test → reject, fewer passed
tests → reject, known-file-fixed → accept. Успіх лише якщо всі 5 збігаються.

## Frontend build і робоче дерево

`npm run build` (gulp/sass) перекомпільовує кілька **tracked** артефактів
(`public/css/app.css`, `plugins/halloween/css/style.css`, `plugins/shots/css/style.css`)
новішими sass/autoprefixer. Це нормальний build-output, не зміна сирців. Скрипт
запам'ятовує `git diff --name-only` до збірки й відновлює з `HEAD` лише ті tracked
файли, які **були чистими** до неї і належать до whitelist build-output
(`public/css/*`, `plugins/*/css/*`). Усе інше не чіпається: файли, змінені/застейджені
до запуску, — теж, а якщо під час збірки змінився tracked-файл поза whitelist
(паралельний письменник у спільному workspace), скрипт друкує
`NOTE: ... not restoring` і лишає його як є. У лог пишеться
`restored N build-generated tracked file(s)`, у підсумку `git status` показує тільки
файли T05.

## Amended restore contract (revision 2)

Після інциденту з паралельним письменником (див. нижче) контракт T05 посилено:

- відновлюються **лише** `public/css/**` і `plugins/*/css/**` — саме те, що пише
  gulp/sass. Whitelist реалізований `case`-патерном; у bash `*` матчить і `/`, тому
  `public/css/*` покриває `public/css/**`;
- скрипт **не викликає** `git restore`, `git checkout`, `git reset` взагалі (restore —
  це read-only `git show HEAD:<path>` + запис файлу);
- будь-який tracked-файл поза whitelist, що змінився під час збірки, лишається як є,
  з рядком `NOTE: <path> changed during the frontend build; not restoring`;
- `git status --porcelain server/` і `git diff -- server/` побайтово однакові до/після
  прогону (sha256 нижче).

Перевірка:

```bash
grep -nE 'git[[:space:]]+(restore|checkout|reset)' scripts/ci/run.sh   # → нічого (exit 1)
before=$(git status --porcelain server/ | sha256sum); bash scripts/ci/run.sh --skip-rust --skip-contract; after=$(...)
```

Факт: `before_status = after_status = 5aabfbdb…f55e1d2`,
`before_diff = after_diff = f323eb65…9a0be7`, `git status --porcelain -- public/ plugins/`
порожній після прогону. NOTE-шлях перевірено реальним випадком: під час збірки T04
дописав `server/src/main.rs`, скрипт надрукував `NOTE: server/src/main.rs changed
during the frontend build; not restoring` і **не** змінив файл (T04 перезаписав його
сам, втрат немає).

## Workflow: що саме закомічено

`.github/workflows/ci.yml` — `name: ci`, тригери `pull_request` і
`workflow_dispatch` (без `push`, без deploy-job, без кроку push, без `secrets`),
`permissions: contents: read`, `concurrency` на ref, `actions/cache` для
`~/.cargo/registry/{index,cache}`, `~/.cargo/git/db`, `server/target` з ключем від
`server/Cargo.lock` + `server/rust-toolchain.toml`. Кроки 1–6 дзеркалять
`scripts/ci/run.sh`; npm-залежності ставляться `npm ci` з npm-кешем. У W0 workflow
не запускається; при рішенні про remote CI (О11) пінимо `uses:` на SHA, як у
`build-and-push.yml`/`delivery-guard.yml`.

## Обмеження / що не робилося

- Жодних змін у `server/**`, `deploy/**`, `backend/**`, `src/**`, `public/**`,
  `package.json`, наявних 3 workflows; прод/staging не чіпалися; без push/commit/deploy.
- `docker compose config` на staging env не запускався.
- `--skip-frontend` пропускає і frontend build, і vitest (обидва — JS-тулчейн);
  це задокументовано в `--help`/`--list`.
- Remote Actions run, docker build без push, media VCL proof, tracker fixtures та
  решта пунктів `pr-verify` з плану §11.2 — поза T05 (G1/W1+).
