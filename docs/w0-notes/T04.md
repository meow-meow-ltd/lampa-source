## 2. O9 — зафіксовані версії (T04-частина)

| Крейт | Пін | Evidence |
|---|---|---|
| `sqlx` | **`=0.8.6`**, `default-features = false`, `features = ["runtime-tokio", "sqlite"]` | `server/Cargo.toml`, `server/Cargo.lock` (`sqlx 0.8.6`, checksum `1fefb893…`); `sqlite` тягне `libsqlite3-sys 0.30.1` (bundled); `cargo test --locked`, `cargo build --release --locked` — exit 0 |
| `libsqlite3-sys` | `0.30.1` (транзитивно, bundled) | `Cargo.lock`; у builder-контейнері є `cc`, bundled-збірка пройшла |
| `rusqlite`, `totp-rs`, `tower-http` | **не додані в T04** (не потрібні) | О9 для них закриває T10 (backup API/TOTP/HTTP-політика); тут не вигадуємо піни |

`default-features = false` прибирає `macros`/`any`/`json`: `sqlx-macros` не збирається
(`cargo tree -i sqlx-macros` → «nothing to print»), тому `query!`/`migrate!`-макросів немає і збірка
не потребує БД. Застереження: sqlx 0.8.6 у власному `Cargo.toml` **безумовно** вмикає
`sqlx-core`-фічі `migrate`/`offline` (це не наши фічі й не вимикається через `default-features`),
тож код migration-модуля присутній у залежності, але **ніколи не викликається**: сервер не має
migrator-а, migration-файлів і не створює `_sqlx_migrations` (перевірено тестами).
`journal_mode` sqlx 0.8 **не виставляє** за замовчуванням (перевірено по джерелу `sqlx-sqlite-0.8.6`:
`pragmas.insert("journal_mode", None)`), тому PRAGMA не додається; режим лише assert-иться.
`create_if_missing` у sqlx за замовчуванням `false`, але T04 додатково вимагає `mode=rw` у URL і
явно ставить `create_if_missing(false).read_only(false)`.

## 3. Ключові рішення / семантика

1. **URL**: тільки `sqlite:<absolute path>?mode=rw`; `ro`, `rwc`, `memory`, `immutable=true`,
   невідомі параметри → `InvalidUrl` до відкриття файла. Файл не створюється ніколи.
2. **Пул**: `max_connections = 1`, `min_connections = 1`, `acquire_timeout = 10 s`.
3. **PRAGMA на кожному з'єднанні**: `busy_timeout=5000`, `foreign_keys=OFF`, `synchronous=FULL`,
   `cache_size=-2000`, `temp_store=FILE`; `journal_mode` не виставляється. Guard *зчитує* всі шість
   значень з pooled-з'єднання й падає fail-closed на будь-яку розбіжність (`pragma_mismatch`).
4. **WAL fail-closed без записів**: спершу перевіряються sidecar-файли (`-wal`/`-shm`) і header
   SQLite (offset 18/19, legacy=1); WAL-файл відхиляється **до** відкриття SQLite, тому конверсії
   journal_mode / створення sidecarів не відбувається.
5. **Guard**: `SELECT version FROM schema_version LIMIT 1` = **7** → `PRAGMA quick_check` = `ok`.
   Будь-який збій → `SchemaGuardError` з стабільним кодом (`missing_file`, `invalid_url`,
   `invalid_header`, `wal_sidecar_present`, `journal_mode_not_delete`, `open_failed`,
   `guard_query_failed`, `pragma_mismatch`, `schema_version_unreadable`,
   `schema_version_mismatch`, `quick_check_failed`); пул закривається, файл не змінюється.
6. **Fail-closed readiness**: `/healthz` = 200 завжди (liveness, без БД); `/readyz` = 200
   `{"status":"ready","db":"ok","schema_version":7}` або 503
   `{"status":"not_ready","db":"unavailable","reason":"<code>"}`. У лог — один `error!` з
   `CRITICAL` і кодом (без SQL-тексту). Процес не падає: деплой-джоба бачить 503.
7. **`ALLOW_UNKNOWN_SCHEMA=1`** — lab-only: пропускає лише перевірку рівності версії; quick_check і
   journal_mode лишаються обов'язковими; при старті — WARN. У `deploy/**`, compose, CI-скриптах
   прапорця немає (grep = 0); у прод-конфізі його бути не повинно.
8. **Settings**: `list`/`get` повертають `admin_password`/`admin_token` як `"***"`; `get_raw`
   доступний лише довіреному коду (auth). Upsert для secret-ключа зі значенням `"***"` — no-op
   (round-trip маскованого GET не псує секрет). `visible` існуючого рядка не змінюється.
   `Delete` повертає `bool`. `Display` помилок не містить SQL/драйвера.
9. **Profiles**: `list` у порожній таблиці створює `Main` (`l_1`, `is_main=1`, `sort_order=1`) в
   транзакції; `create` — trim імені, `l_1` за замовчуванням, `max(sort_order)+1`; `update` —
   patch лише переданих полів (порожні рядки ігноруються, порожній patch → `no_fields_to_update`),
   `updated_at=now ms`; `delete` — **plain DELETE без каскаду**, orphans у `bookmarks`,
   `profile_settings`, `timeline_events` лишаються (FK у схемі немає, `foreign_keys=OFF`).
10. **Жодного DDL/міграцій у runtime**: `raw_sql`/`CREATE` існують лише в `#[cfg(test)]`
    helper та `tests/**`; фікстура не застосовується сервером.

## 5. Незмінні інваріанти (для G1)

- `schema_version` = 7 (DDL/`ALTER`/`VACUUM`/`ANALYZE`/WAL відсутні в runtime).
- `journal_mode` = `delete` до і після записів; WAL-файл відхиляється без конверсії.
- `_sqlx_migrations` не створюється (тести `sqlite_master` це доводять); migration runner не
  викликається; compile-time query macros відсутні (`sqlx-macros` не збирається); збірка не
  потребує БД. Примітка: `sqlx-core/migrate`-код присутній як залежність sqlx 0.8.6 (див. §2).
- `Pool` max/min = 1; `mode=rw`; PRAGMA-пакет як у D9/§4.2; `busy_timeout=5000`.
- `/healthz` не залежить від БД; `/readyz` 503 при будь-якому збої guard.
- Репозиторії: секрети маскуються, SQL-помилки не течуть в API, delete профілю без каскаду.
