## 2. Синтетична БД — походження і інваріанти

* **Схема (schema-only, без жодного рядка даних)**: додані statements звірені з read-only
  `SELECT sql FROM sqlite_master` стендової копії та з міграціями `backend/database.js` (v1…v7).
  Результат: `sqlite_master` (без `sqlite_sequence`, 18 об'єктів) **рівний** і `schema7.sql` (T04),
  і стендовому v7 — `mine == schema7: True`, `mine == staging: True`.
  Два прийоми виправлені свідомо: `profiles.sort_order` додано через legacy-текст `ALTER`-а
  (кома з нового рядка), а індекс `timeline_profile_id` **прибрано** — його створює міграція v1,
  але міграція v2 видаляє таблицю, на якій він тримається, тому у справжньому v7 його немає.
* **Рядки**: усі константи з коду скрипта (`golden-*`, T0 = 2026-01-01T00:00:00Z,
  `card_id` 1001…3002, `golden-hash-000a…001e`, `192.0.2.x`). Жоден рядок не зчитано з
  `/opt/lampa/data` чи стендової копії; `--out` у ці каталозі **відмовляється** писати (fail-closed).
* **Інваріанти**, які будівник асертить перед виходом: `schema_version=7`, `journal_mode=delete`,
  `profiles=3` рівно один `Main`, `bookmarks=12 ≤ 20`, `timeline_events=10 ≤ 50`, `settings=20`
  (точно 20 ключів defaults з `backend/database.js`), `device_access=3` з рівно одним `allowed`,
  `bookmark_events` без сиріт (кожен `entity_id` існує в `bookmarks`), `integrity_check=ok`,
  таблиці = 10 app + `sqlite_sequence`, **немає** `_sqlx_migrations` і sidecar `-wal/-shm/-journal`.
* **Детермінізм**: два послідовні побудови дають однаковий `content_sha256`
  `6745537d86f2343e…` і навіть байт-ідентичний файл `e6b77750c412b51a…` (98 304 B).
  Це і є причина, чому `--check` відтворюваний: свіжа однакова БД → ті самі рядки → ті самі
  відповіді після нормалізації.

## 3. Механіка захоплення

1. Тимчасовий робочий каталог `<repo>/../.golden-capture-tmp/capture-*` (поза git),
   туди ж — `database.sqlite`; у кінці `docker rm -f -v` + `rmtree` (у `finally`).
2. `docker create --name lampa-golden-<pid>-<rand> -p 127.0.0.1:9121:3000 -v <db>:/data` з
   **закріпленим digest-образом** `ghcr.io/meow-meow-ltd/lampa-source@sha256:d678c142…21add7`
   (той самий, що в `deploy/compose.staging.yaml`), `pull` заборонений — образ має бути локально.
   Порт перевіряється на вільність; **9119/9118 ніколи не використовуються**.
3. Env контейнера: лише `DB_PATH=/data/database.sqlite`, `HOST`, `PORT`, `TOTP_SECRET` —
   **синтетичний**, генериться у скрипті. Файли env стендa/прода не читаються, їхні значення
   нікуди не потрапляють (сканер це перевіряє).
4. Readiness: `GET /` → 200 (≤60 s; фактично ~1 s, бо `gulp default = serve` без перезбірки).
5. Setup-крок (поза 27): `POST /admin/login` → cookie `auth_token`; далі запити йдуть **у фіксованому
   порядку 1..27** з `auth_token` для admin-маршрутів (2–6) і з `device_token`, виданим фікстурою 01,
   для решти (7–25); 26/27 — без cookie. `User-Agent: lampa-golden/1.0` фіксований.
6. Очікуваний статус усіх 27 — 200; будь-яка інша відповідь = fail-closed (exit 1/2), а не «золотий»
   статус 401. Спец-перевірка: фікстура 01 мусить повернути `ok=true` + `device_token`
   (інакше — помилка про TOTP-вікно/годинник).
7. Тиша після прогону: `docker ps -a --filter name=golden` — порожньо, робочого каталогу немає;
   `lampa-staging` (9119) і `lampa` (9118) — `Up`, RestartCount не чіпалися.

## 5. Формат артефактів

* Файли фікстур: `NN_<method>_<path>.json` (27 шт.), `route` — **паттерн** контракту
  (`DELETE /api/settings/{key}`), `request.path` — конкретна ціль (`/api/settings/head_notice`).
* `manifest` лежить у `server/tests/fixtures/api/manifest` **без розширення** навмисно:
  контракт верифікації вимагає, щоб `ls server/tests/fixtures/api/*.json | wc -l` дорівнював **27**,
  тоді як маніфест теж має бути у цьому каталозі. Це JSON (`json.load`/`serde_json` читають його

  детермінований (без таймстемпів), тому входить у diff `--check`.

## 8. Спостереження / передача далі

- **manifest без `.json`** — свідоме рішення під `ls *.json == 27` (див. §5); якщо G1 захоче
  `manifest.json`, достатньо перейменувати файл і прибрати цей абзац — контент не змінюється.
- **T07–T09** можуть споживати фікстури як `{index, route, request, response{status, headers[][],
  body(string)}}`; `headers` — впорядковані пари `[name, value]` (порядок збережено з відповіді),
  `body` — рядок legacy-байтів після R1–R9. Очікувані статуси — 200 для всіх 27.
- **Нормалізація — частина контракту**: якщо зміниться тіло/порядок/кодування відповіді, `--check`
  впаде з конкретним JSON-путем різниці (перші 20 diffs друкуються), а не мовчки «перепише» фікстури.
- **Прод-БД змінюється ззовні**: за прогони T03 `timeline` у `/opt/lampa/data` підріс 643→644
  (живий контейнер), `bookmark_events`/`timeline_events` теж рухалися — це **не** ефект T03
  (захоплення відкриває лише власний тимчасовий файл; див. також нотатку T04 §6). Саме тому
  prod-проба у звіті «informational», а асертується лише незмінність рядків **staging** (рядок 7),
  який ніхто крім smoke не пише.
- Фікстури **мутують** стан синтетичної БД (create→delete профілю, PUT/DELETE settings,
  add→remove→clear→sync закладок, timeline update) — це частина контракту; саме повторна побудова
  свіжої БД робить прогін відтворюваним. На стендовій/прод копії жодна мутація не виконується.
- Якщо T05/CI підв'яже `--check`, потрібні локальний docker + pinned-образ; за їх відсутності
  скрипт падає fail-closed із зрозумілим меседжем (exit 2), а не «зеленіє» без захоплення.
